# 3보드 통신 검증 Case Study

## 프로젝트 배경

교육용 3보드 환경에서는 하나의 입력이 여러 소프트웨어와 통신 구간을 지나 최종 상태 변화로 이어졌습니다. 저는 각 보드가 개별적으로 동작하는지만 확인하는 대신, 통신 중단과 반복 이벤트가 전체 경로에서 어떻게 처리되는지 질문으로 정리했습니다.

## 역할 구분

교육 환경은 보드, 운영체제, 통신 드라이버, IPC/CAN 예제와 기본 펌웨어를 제공했습니다. 저는 그 환경에서 시험 시나리오를 정하고 heartbeat 송신기, 상태 검증 도구, evidence 기록 형식과 단위 테스트를 작성했습니다.

공개 저장소에는 업체 제공 코드와 프로토콜 세부 내용을 넣지 않았습니다. `src/validation_state_machine.py`는 당시 검증 논리를 설명하기 위해 일반 이벤트 기반으로 다시 작성한 코드입니다.

## Heartbeat 장애와 복구

500 ms 주기로 heartbeat를 보내고 마지막 유효 메시지 이후 2초가 지나면 timeout으로 판정했습니다. 세 번의 반복 시험에서 관측한 timeout은 각각 2000.136 ms, 2044.158 ms, 2043.406 ms였습니다.

당시 검증 도구는 통신이 복구되어도 `SAFE`를 유지하고 수동 reset 후 `AUTO`로 돌아가는 정책을 사용했습니다. 이것은 실험 조건을 명확하게 만들기 위해 선택한 정책이며 제품의 공식 안전 요구사항으로 해석하지 않습니다. 공개 예제에서는 자동 복귀 정책도 선택할 수 있게 분리했습니다.

## 반복 이벤트 처리

첫 운전자 개입 이벤트에서는 `AUTO`에서 `DRIVER`로 한 번 전이했습니다. 이후 같은 종류의 이벤트가 다시 들어오면 별도 duplicate로 기록하고 상태를 `DRIVER`로 유지했습니다.

이 시험으로 확인한 것은 수신 애플리케이션이 반복 이벤트 때문에 추가 상태 변화를 만들지 않는다는 점입니다. 물리 CAN 버스에서 같은 frame이 반복된 원인까지 확인한 것은 아닙니다.

## 판정 기준

기능 판정과 물리계층 판정을 분리했습니다.

- 기능 확인: 이벤트 수신, 상태 변화, 중복 억제, evidence 기록
- 미확인: CAN 차동 파형, ACK, transceiver 상태, 자동 재전송의 실제 발생 여부

따라서 수신 경로는 기능 PASS로 기록했지만 물리 버스의 원인은 확인하지 않은 상태로 남겼습니다.

## 배운 점

관측 지점이 하나뿐이면 정상 동작과 원인을 같은 말로 설명하기 쉽습니다. 이번 프로젝트에서는 확인한 결과와 확인하지 못한 원인을 분리하고, 같은 조건을 반복할 수 있도록 상태와 시간을 로그로 남기는 방식을 익혔습니다.
